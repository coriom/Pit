## Constant-product model and precision

Inputs are manually labeled token0 and token1 with separate decimals `d0,d1` and positive raw reserves `X,Y`. Labels never establish chain-scoped identity. Human reserve price `P = (Y × 10^d0)/(X × 10^d1)` is token1 **per one token0**; reverse price is its reciprocal. The exact numerator and denominator are retained as decimal strings in the report; 18-decimal display ratios round **down**. The invariant is retained as the exact **raw** product `X×Y`, with separate `invariantHumanDecimals=d0+d1`; the UI never misformats a 72-decimal product through the 36-decimal token formatter.

For source reserve `S`, destination reserve `D`, input `I` and whole pool fee `f` bps:

`E = floor(I(10000−f)/10000)`; `O = floor(DE/(S+E))`; post-reserves are `S+I` and `D−O`. Thus the entire input, including fee retained by the pool, increases source reserves. Fee-free output substitutes `I` for `E`. Relative reserve impact uses `1 − O_feeFree/(I×D/S)`, while fee-inclusive deviation substitutes actual `O`. Both display as 18-decimal fractions; neither is slippage protection or a PIT fee. Average execution price is output-token units per input-token unit. Post-swap marginal price is recomputed from integer-rounded reserves. The model rejects an output that rounds to zero and verifies the post-swap invariant never falls below the starting invariant.

For proportional liquidity, a desired token0 amount and available token1 budget set the affordable token0 amount; paired token1 rounds down to a raw unit. The full desired token0 pairing rounds up to show its conservative requirement. New-provider share is `usedToken0/(reserve0+usedToken0)`. A separate withdrawal example floors each reserve multiplied by withdrawal bps / 10000. A sub-raw-unit reserve-ratio residual may remain after rounding. Empty pools are explicitly unsupported, and no precise on-chain LP-token minting claim is made.

Independent `Decimal` 70-digit reference: with reserves 100 and 10,000, the spot price is 100 token1/token0 and reverse 0.01. For 10 token0 in with zero fee, continuous output is `909.090909090909…`; at six token1 decimals the modeled output is exactly raw `909090909`. Continuous fee-free impact is `9.090909090909…%`; continuous post-swap marginal price is `82.644628099173…`. The integer-rounded reserve product is at least its starting value. A 10/1000 proportional deposit leads to reserves 110/11000 and new-provider share `10/110 = 9.090909…%`.

## Concentrated continuous-range model

Official [Uniswap v3 Math Primer Part 2](https://blog.uniswap.org/uniswap-v3-math-primer-2) and the [v3 whitepaper](https://app.uniswap.org/whitepaper-v3.pdf) motivate the bounded continuous formulas. This calculator does **not** implement Q64.96, TickMath, NFT positions, on-chain fee growth or exact contract rounding. Official [v3 architecture concepts](https://developers.uniswap.org/docs/protocols/v3/concepts/architecture) inform the explicit separation from protocol execution.

The manually entered price `P` is token1 per token0, already normalized for human token decimals. Let `a=√Pa`, `b=√Pb`, `q=√P`, `u=clamp(q,a,b)`, with `0<Pa<Pb`. Continuous amounts for liquidity `L` are `token0=L(1/u−1/b)` and `token1=L(u−a)`. Below the lower bound only token0 remains; above the upper bound only token1 remains. Exact boundary equality is a composition convention and **not** a claim about live active-tick state.

Each decimal price is parsed exactly at 18 places, bounded to `[10^-12,10^12]`, and multiplied by `10^18` before an integer square root. The computed root is `floor(√(priceRaw×10^18))`, so its approximation is below the mathematical root by **less than 10^-18 in square-root-price units**. The integer square-root loop is bounded to 256 iterations. For the supported range, a root collision between distinct entered bounds is rejected. The token-amount formulas use that fixed root and floor once to raw token units; this does not bound the full continuous-model token error to one raw unit because reciprocal-root sensitivity can amplify root truncation, especially near the minimum price. Users should treat the model as a bounded deterministic approximation, not contract-equivalent precision.

The feasible `L` is the floor of both positive budget-derived limits: `budget0 × u×b/(b−u)` and `budget1/(u−a)`, with decimal scales applied. A zero coefficient does not constrain that budget. The engine checks final rounded token use against each supplied budget, reports unused amounts, and rejects zero or out-of-bound L. Amounts and valuations floor to destination raw units. Maximum raw input/budget and L are bounded to `10^36`; outputs must fit the existing 256-bit raw bound. These restrictions deliberately exclude extreme pools.

At scenario price `P1`, LP value is `futureToken0×P1 + futureToken1` in token1. HODL value uses **initially used** token0 and token1 at the same `P1`. Their signed difference and fraction over positive HODL value are shown. A negative relative difference need not mean the LP's absolute value fell. Separately entered accrued token0 fees are valued at `P1`; token1 fees add directly. Break-even fees before cost are `max(0,HODL−LP)`; with known token1 costs `C`, required fees become that amount plus `C` and net difference is `LP+statedFees−C−HODL`. Unknown management/gas cost yields INCOMPLETE and no net assessment. A pool fee tier is never treated as earned LP revenue.

Independent high-precision continuous reference: `Pa=.25`, `Pb=4`, `P0=1`, `L=100` gives initial `(token0,token1)=(50,50)` and value 100 token1. At `P1=4`, LP is `(0,150)`, value 150, while HODL is 250: difference −100 or −40%. At `P1=.25`, LP is `(150,0)`, value 37.5, HODL 62.5: −40%. At `P1=4`, break-even fees are 100 token1 before costs and 105 with a known 5-token1 cost. These cases were independently reproduced with Python `decimal.Decimal` at 70-digit precision. All are fee-free continuous reference values except the explicitly added hypothetical cost.

## Contracts, browser boundary and isolation

`amm-pool-math` and `concentrated-liquidity` alone were added to the reviewed `local-pure` allowlist. Runtime adapters validate exact mode-specific input shapes, numeric engine constraints, result structure and conservation identities. Outputs carry versioned raw decimal strings, explicit token labels/decimals and units. Future workflow port compatibility rejects manual-label token identity; it cannot infer sameness from a ticker, reverse a price direction, or treat illustrative L as a native-token quantity. Unknown fees/costs do not become zero. The browser forms only bundle these pure engines and create local Blob JSON downloads; no wallet, RPC, storage or transaction API is imported.

The frozen `READ_ONLY_TOOL_IDS` still lists only six existing calculators. `pnpm beta:check` built eight HTML pages and one CSS asset with no wallet/trading bundle; the reviewed host package SHA-256 remained `f2907ac694594531e16ab5501e3be7d066edf98f528553f2bf2164dde725a425`. No Vercel action occurred. Phase AL identified a Tailwind v4 global content-scanning fragility: unrelated code or documentation tokens can change beta CSS. Official [Tailwind source detection guidance](https://tailwindcss.com/docs/detecting-classes-in-source-files) supports explicit `source(none)` plus scoped `@source` paths. Because this phase did not cause beta drift, no speculative styling change was made. Phase AO should evaluate a durable scoped-source migration against the frozen package bytes and browser presentation; domain terminology must not be obfuscated to suppress a generated class.
