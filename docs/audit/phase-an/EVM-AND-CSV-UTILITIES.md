## EVM methodology and precise limits

[EIP-55](https://eips.ethereum.org/EIPS/eip-55) uses Ethereum Keccak-256 of lowercase address hex text to determine uppercase checksum letters. A 20-byte hex address is only syntax. Fully lowercase/uppercase text is `NOT_CARRIED`, while mixed-case text is `VALID_EIP55` or `INVALID_EIP55`. The optional `eip155:<chainId>:<checksummed-address>` descriptor is manual metadata; it neither verifies an account nor implements chain-dependent checksum variants. A valid checksum does not verify a recipient.

The [Solidity ABI specification](https://docs.soliditylang.org/en/latest/abi-spec.html) defines selectors as the first four bytes of Keccak-256 of a canonical function signature, and non-anonymous event topic0 as the full digest. The inspector rejects spaces, aliases such as `uint`, parameter names, arrays, tuples and dynamic types. Supported canonical static primitives are `address`, `bool`, `int8`…`int256`, `uint8`…`uint256` in 8-bit steps, and `bytes1`…`bytes32`. A signature is at most 512 characters with at most eight arguments. No remote signature database is consulted.

Calldata decoding accepts one function object or an array of at most eight function objects in JSON (`type`, `name`, `inputs`, each input with `name` and `type`). ABI input is at most 8 KiB; calldata at most 4 KiB. The parser rejects unsupported fields, duplicate/ambiguous selectors, unsupported types, wrong selectors, truncated words and trailing bytes. Only one 32-byte word per static argument is accepted. Parameter names and decoded data remain untrusted text and are rendered with `textContent`. Decoding does not simulate or execute a call and proves nothing about contract safety or transaction success.

Independent published vectors: EIP-55 `0x52908400098527886E0F7030069857D2E4169EE7`; `transfer(address,uint256)` → `0xa9059cbb`; `approve(address,uint256)` → `0x095ea7b3`; `Transfer(address,address,uint256)` → `0xddf252ad1be2c89b69c2b068fc378daa952ba7f163c4a11628f55a4df523b3ef`. Fixed ERC-20 transfer calldata to that address with final word `0x64` decodes to amount decimal `100`. Ethereum Keccak-256 is **not** standardized SHA3-256.

## CSV grammar, normalization and export safety

The parser implements a strict bounded [RFC 4180-style quoted-field subset](https://www.rfc-editor.org/rfc/rfc4180): UTF-8 with optional BOM; comma, semicolon or tab chosen explicitly; CRLF/LF rows; quoted delimiters, escaped quotes and quoted newlines. It rejects malformed quote transitions and unterminated fields. The browser reads the selected file with fatal UTF-8 decoding. Pure input is limited to **256 KiB, 1,000 data rows, 30 columns and 2,048 characters per cell**. Duplicate or blank confirmed headers are rejected. Structural width issues are reported. Candidate delimiter counts are hints; the user explicitly confirms delimiter and header and inspects the original preview before transformation.

The generic mapped fields are `recordId`, `chainId`, `eventId`, `timestampUtc`, `amount` and `note`. Mappings must refer to distinct existing source columns. A mapped empty value is `MISSING`, an invalid value is `INVALID`, an unused field is `UNMAPPED`, and explicit numeric zero is `NORMALIZED` with raw value `0`. No monetary or token identity is inferred. Amounts are signed, ungrouped decimal strings with explicitly chosen 0–18 places; excess precision, locale separators and exponent notation are rejected. BigInt produces the exact signed smallest-unit integer. Timestamp formats are selected explicitly: ISO with `Z` or numeric UTC offset, UTC date at midnight, or Unix seconds. Calendar and offset validity is checked; no `Date.now()` or guessed locale format is used.

Deduplication uses 1–4 distinct mapped, populated identity fields. Keys are deterministic JSON arrays of normalized values, not ticker/timestamp/amount guesses. A group reports whether non-identity fields conflict. Every row in a duplicate group needs an explicit keep/exclude choice and each group needs at least one kept row; the source text remains unchanged in memory. Incomplete or invalid normalization blocks normalized CSV export. The exact machine-readable JSON report includes original text, mapping, raw values, statuses, decisions and limitations; it is **not** a Taxlot schema. The unmodified download is explicitly labelled spreadsheet-unsafe. The reviewed CSV quotes every cell and prefixes an apostrophe if leading whitespace/control characters precede `=`, `+`, `-` or `@`; quoting alone is insufficient spreadsheet formula protection. The prefix intentionally changes CSV text while exact JSON preserves the original.

Independent examples: `1.250000` at six places becomes raw `1250000`; explicit zero becomes raw `0`; `2026-01-02T10:00:00+02:00` becomes `2026-01-02T08:00:00.000Z`. In the fictional three-row sample, rows 1 and 3 have the same selected chain/record/event identity; keeping row 1 and excluding row 3 yields two retained data rows. A changed note marks a conflict. `=SUM(1,1)` is exported in spreadsheet-safe CSV with an apostrophe prefix and remains exact in JSON. These are data-preparation examples, not transaction or tax conclusions.
