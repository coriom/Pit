## Rebalance mathematics and conservation

All entered values are nonnegative decimal strings in one explicitly named manual currency, represented as 18-decimal BigInt raw units. A blank valuation stays unknown. There are 2–12 uniquely identified rows, and target weights are whole bps summing **exactly 10,000**. Row labels are display metadata, not token identities. The input magnitude is bounded to 256-bit raw integers; labels, input lengths, row counts and shocks are bounded. No floating-point monetary intermediary is used.

For total included value `V = Σvᵢ` and target bps `wᵢ`, the unrounded ideal is `V × wᵢ / 10000`. The engine floors each value to the smallest manual-currency unit, then assigns remaining units by largest remainder, breaking equal remainders by stable local row ID. Thus `Σtargetᵢ = V` exactly. Current weight is `vᵢ/V`, displayed to the nearest ppm; signed allocation drift is target weight minus that displayed current weight in ppm. Independently rounded weight/drift displays need not sum to precisely one million ppm. Signed ideal value change is `targetᵢ − vᵢ`. Gross traded notional is `Σ|changeᵢ|`; one-way turnover is gross/2 because pre-fee value is conserved. The optional fee estimate is `ceil(gross × feeBps / 10000)` and remains **separate**; it does not imply the fee-funded final allocation still equals the target.

With contribution `D ≥ 0`, the desired allocation is computed from `V + D`. Exact no-sale feasibility requires every `targetᵢ ≥ currentᵢ`; contributions are then `targetᵢ − currentᵢ`, nonnegative and summing to `D`. Infeasible rows show their blocking overweight instead of negative purchases. A positive holding with zero target weight has no finite contribution-only solution. Otherwise the minimum deposit is the smallest raw-unit `D` for which the apportioned targets cover every current row. The bounded search checks at most 10,001 adjacent raw totals after an algebraic lower bound; it does not assume largest-remainder apportionment is monotone. A zero-value starting set requires at least one smallest unit before an allocation exists. Residual cash is always accounted for in the apportionment rather than created or lost.

For manually stated shock bps `sᵢ` from -10,000 to +100,000, projected bucket value is `round-half-up(vᵢ × (10000+sᵢ)/10000)`. The projected total is the sum of these rounded values; change is projected minus starting total; projected weights use the **projected** total. Largest starting/projected weights are concentration descriptions, not risk forecasts. A 100% total loss has a defined monetary change but undefined post-shock allocation weights.

Independent reference arithmetic: `600 + 400 = 1000`; at 50/50 the desired values are 500/500, signed ideal changes -100/+100, gross notional 200 and one-way turnover 100, or 10% of starting value. A 1% stated fee on gross is a **separate** estimated 2, not wealth lost through turnover itself. A 200 deposit gives desired 600/600 and contributes 0/200; a 100 deposit gives desired 550/550 and cannot meet the target without selling. The minimum deposit is 200. Shocks -20% and +10% produce 480 and 440, total 920, change -80 (-8%), and projected weights 480/920 ≈ 52.1739% and 440/920 ≈ 47.8261%. The golden values follow integer multiplication and fractions independently of the implementation.

## Historical returns, drawdown and rounding

Historical input is 2–30 strictly increasing `YYYY-MM-DD` dates (calendar-validated, years 1900–2100), nonnegative 18-decimal ending values and signed external flows. The first snapshot has zero flow. A positive flow is a deposit; a negative flow is a withdrawal. Each interval's flow occurs **at the end, immediately before the ending snapshot, and is included in the reported ending value**. Therefore `preFlowEndᵢ = endᵢ − flowᵢ` must be nonnegative and `periodReturnᵢ = preFlowEndᵢ / endᵢ₋₁ − 1` requires a positive previous ending value. Unknown intraperiod flow timing cannot be repaired from these snapshots; users must add appropriate valuation boundaries. Zero previous value yields INCOMPLETE percentage results, while a complete loss from a positive prior value is -100%.

Nominal monetary gain is exactly `closing − opening − ΣexternalFlows`, in raw units. Chained time-weighted return is the rational product `Π(preFlowEndᵢ/endᵢ₋₁) − 1`. Each fraction is reduced by greatest common divisor; the rational numerator/denominator have an 8192-bit safety cap. The normalized flow-neutral index begins at 1 and applies the same return product. Dates use integer calendar days; no implicit observation clock or interpolation exists. Percentage and index display fields are rounded half-up to 18 decimal places (percent fields represent percent, not fractional return). Raw input values and exact decimal-string output fields remain in local JSON reports. The rational comparison, rather than a rounded display index, determines high-water marks.

Drawdown at a snapshot is `index/currentHighWater − 1`; the result is between 0 and -100%. Maximum historical drawdown retains the earliest trough on ties; an equal high resets the reference peak date to the latest equal-high date for later underwater duration. Recovery is the first later supplied snapshot at or above the maximum-drawdown peak. Current underwater duration is calendar days since the last high; peak-to-recovery duration is calendar days. No recovery is reported when no such supplied snapshot exists.

Independent reference arithmetic: opening 100, next ending 160 including a +50 end-period deposit gives pre-flow value 110 and +10% return. The following ending 144 with no flow gives -10%. The exact chain is `1.10 × 0.90 = 0.99`, so TWR is **-1%** and normalized index runs 1, 1.10, 0.99. Monetary gain is `144 − 100 − 50 = -6`; the deposit does not create investment return. Drawdown from 1.10 to 0.99 is **-10%** despite the larger raw balance. These figures are manual examples, not verified market performance or money-weighted IRR.

## Contracts, interface and privacy

The closed pure-local allowlist adds only `portfolio-rebalance` and `performance-drawdown`. Thin v1 adapters validate exact mode-specific object shapes, nested string rows, structured input errors and raw-string output/conservation identities. Additive unit kinds distinguish manual-money, weight-bps, signed manual cash flow and normalized performance index. Automatic compatibility rejects these manual/dated outputs and incompatible dates or currencies; the registry provides no wallet or execution power. Existing AG/AH/AI meanings and calculations are unchanged.

Each Astro page has one visible mode at a time, labelled manual inputs, an illustrative sample, prominent result, secondary row detail, limitations and local JSON download. The report retains raw values, assumptions, version and an explicit manual-data disclaimer. Form data is not placed in URLs, persistence, analytics or a remote API. Browser checks intercept external and same-origin API requests and spy on wallet, IndexedDB and Web Storage. No new framework, charting dependency, CSV importer or workflow engine was introduced.
