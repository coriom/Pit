The operator generates a passphrase-protected GPG encryption keypair on an **independent recovery machine**, retaining two protected private-key copies outside Netcup. Loss of that key makes every encrypted archive unrecoverable. Only the public certificate and its pinned 40-hex fingerprint are installed on Netcup. The private key never goes to Netcup, Git, Coolify or R2. The PIT-only R2 S3 token has `Object Read & Write` restricted to this one bucket; a separate account administrator configures a seven-day object lifecycle for prefix `pit-v2/`. Cloudflare documents bucket-scoped object tokens and prefix-scoped lifecycle rules. The token cannot change bucket lifecycle settings. Sources: [R2 token permissions](https://developers.cloudflare.com/r2/api/tokens/), [R2 object lifecycles](https://developers.cloudflare.com/r2/buckets/object-lifecycles/).

On Netcup, `/etc/pit-v2-offsite` is root-owned `0700`; `config.json`, `recipient.asc` and `rclone.conf` are root-owned `0600`. `rclone.conf` contains only one remote, `pit_v2_r2`, with a PIT-bucket-scoped access key and the verified account endpoint. No token or public-key fingerprint is embedded in Git. The existing `/var/backups/pit-v2` archives remain root-only. `pit-v2-offsite.py` verifies the local dump and SHA-256 sidecar, imports the pinned **public-only** key into a temporary GPG home, encrypts with AES-256 OpenPGP, uploads only the `.gpg` ciphertext to `pit-v2/YYYY/MM/`, downloads it to verify its SHA-256, then uploads and reads back a small JSON metadata file. It refuses a mismatched recipient, symlinks, weak file modes, stale/oversized archives, unexpected R2 endpoint, duplicate mutable objects, or a projected PIT prefix above 8 GiB. `rclone copyto --immutable` prevents overwrite of a different existing object. No plaintext dump is uploaded. The JSON metadata exposes only the archive name, hashes, size and recipient fingerprint; it is not encrypted.

Cloudflare lifecycle should expire both `.gpg` and `.json` objects after seven days. Deletion can lag the expiration by about 24 hours, so the 8 GiB script cap is an additional bound, not a billing guarantee. A token on the VPS with object write permission may also be able to delete or replace PIT objects if the VPS is compromised. This design protects against VPS/SSD loss; it does not establish immutability against malicious control of the VPS or the R2 account. Verify the independent recovery key backup and account controls before storing customer data.

## Local rehearsal and exact recovery boundary

`python3 backend-rust/ops/test-pit-v2-offsite.py` passed on disposable local PostgreSQL 16 and GPG. It applied the V1/V2 PIT migrations, populated one completed job, one monitor and one alert, created a custom-format dump, and generated a test-only keypair. The upload code received only the test public key. A local object-store fixture accepted **only** ciphertext and JSON metadata; readback checks passed. An independent GPG home holding the test private key decrypted the downloaded copy and restored it into a generated disposable database; all six PIT tables and `jobs|monitors|alerts=1|1|1` passed. The disposable database was removed. A modified ciphertext, an exhausted 8 GiB inventory and a bad source checksum were all rejected. This proves the local encryption/restore path, **not** Cloudflare R2 transport, hosted backup scheduling, or an external restore from a real R2 object. `systemd-analyze verify` accepted the candidate service/failure units.

For a real recovery, download the `.gpg` and `.gpg.json` objects to a separate recovery machine with a PIT-bucket read credential. Verify their provenance and run `pit-v2-offsite-recover.py <archive.dump.gpg> <archive.dump.gpg.json> <private-gnupg-home>` against a local Unix-socket PostgreSQL 16 instance with `PGHOST`, `PGPORT` and `PGUSER` set. It checks ciphertext SHA-256, requires the matching private key, decrypts into a `0700` temporary directory, verifies plaintext SHA-256 and PIT archive contents, creates a randomly named `pit_v2_offsite_restore_*` database, checks the six-table schema and job/monitor/alert counts, then drops the disposable database. It never targets the live `pit_crypto_v2` database. The recovery machine must have enough free space for the ciphertext, plaintext and PostgreSQL restore.
