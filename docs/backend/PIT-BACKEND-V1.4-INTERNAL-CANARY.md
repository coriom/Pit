# PIT Crypto backend V1.4 — internal-only Netcup canary

**Scope:** a new Coolify Compose resource named `pit-crypto-backend-canary`, with one API, one worker, one dedicated PostgreSQL instance and one-shot migration. This is a **proposal, not a deployed resource**. No public hostname, Traefik router, host port, Cloudflare gateway, real customer data, email delivery, signing, broadcast or payment collection is in scope. The five tools remain implemented; hosted NFT metadata fetching is disabled until an independent outbound restriction is proven.

## Immutable inputs and boundaries

- Compose: [`backend/compose.canary.yml`](../../backend/compose.canary.yml). API and worker use `ghcr.io/coriom/pit-backend@sha256:b9e9c812e00b0a782c92579c22254941dddc81ca7b24fd49077acb7525486000`, published from runtime source commit `a4333fcaf2c6d9987702d80305abc7a98256f010`. V1.4 changes only deployment packaging, local operational scripts and documentation; the image runtime source is unchanged.
- PostgreSQL: `postgres@sha256:43f9275df91e012c3da3d86bea5d7bb5e67a473296cc906c5f9e80b8176b1a37`, the read-back `linux/amd64` manifest for PostgreSQL 16.15. The VPS reported `x86_64` on 2026-11-11.
- Expected Compose project: `pit-crypto-backend-canary`. Networks: `pit-crypto-backend-canary_pit-data` (`internal: true`) and `pit-crypto-backend-canary_pit-rpc` (outbound bridge). Volume: `pit-crypto-backend-canary_pit-db-data`. PostgreSQL and migration join only `pit-data`; API and worker join both PIT networks. No service joins any proxy or neighboring project network. An outbound bridge is **not** a general firewall: fixed public RPC use remains permitted, while user-controlled NFT fetches are disabled.
- Every service has `traefik.enable=false`, no `ports` declaration, no proxy labels and no public hostname. The API's image-level `EXPOSE 8789` and PostgreSQL's `EXPOSE 5432` are metadata only; runtime `HostConfig.PortBindings` must be empty. Coolify-generated labels, project/network names and port bindings must be reviewed before any container starts. Any unexpected public route or network attachment fails the canary gate.
- API 0.25 CPU/256 MiB, worker 0.5 CPU/512 MiB, database 0.5 CPU/512 MiB, one-shot migration 0.25 CPU/192 MiB. One API and one worker only. API accepts at most 32 simultaneous requests; one worker processes jobs serially. One invitation is limited to 10 jobs/minute, 20/day and three active monitors. CPU quotas are ceilings, not reserved CPU. The authorized VPS snapshot reported about 743 MiB used by 12 running containers, about 6.3 GiB host RAM available and 143 GiB disk free; these are snapshots, not sustained headroom proof.

## Safe secret injection

Before the approved rollout, create **new PIT-only** random values outside Git: a database password of at least 32 characters, an HMAC key of at least 32 characters, and a disposable canary invitation of at least 32 characters. Inject the password, matching URL-encoded `postgres://pit_api:<password>@pit-db:5432/pit_crypto`, HMAC key and lowercase SHA-256 of the invitation through the new Coolify resource's private environment configuration. Keep the raw invitation in a VPS file owned by the operator with mode `0600` for smoke testing; never put it in command arguments, Git, browser assets or reports. Do not reuse another project's credentials. `PIT_ALLOWED_ORIGIN` is fixed to loopback and there is no browser client. Do not set SMTP variables or allowed email recipients.

The source render and Coolify-generated Compose must pass `node backend/ops/check-canary-config.mjs` using JSON from `docker compose config --format json`, streamed directly to stdin so rendered secrets are not saved or printed. This guard checks exact project/services/images, PIT-only networks and volume, disabled Traefik, absent published ports, limits, read-only application filesystems, NFT/email disablement and consistent database identity. It intentionally fails if Coolify adds an unreviewed route, network, volume or service. Inspect the actual generated configuration **before starting** containers; a passing source render alone is insufficient.

## Approved-rollout sequence and local smoke

1. Record DeOpt and HBI HTTPS health, VPS available memory/disk, container restart/OOM counts, and the absence of a pre-existing PIT canary resource. Do not modify neighbors or the shared proxy.
2. Create only the reviewed PIT Coolify Compose resource with **no domain**. Inspect the generated Deployable Compose, run the fail-closed config guard, and stop before container start if its network, labels or ports differ. Confirm no automatic public routing was attached.
3. Inject PIT-only secrets privately, pull the two immutable images, start PostgreSQL, run migrations `001_init.sql` and `002_edge_nonces.sql`, then start one API and one worker. Require healthy database, API and worker. No host ports or proxy network may appear at runtime.
4. From a checkout of the reviewed source commit on the VPS, run `node backend/ops/run-internal-canary.mjs /secure/pit-canary-invite`. The runner discovers **only** containers labelled with the exact PIT Compose project; verifies image digests, health, Traefik labels, networks, no host bindings, read-only filesystems and effective cgroup CPU/RAM limits; then runs the local smoke script inside PIT's API container. It checks migrations, worker heartbeat, Base Sepolia chain ID, unsigned-origin denial and HMAC replay denial. It stops/restarts **only the PIT worker**, creates one synthetic read-only event job for the known paid-router block 51698212, checks two canonical logs and full coverage, exports, capability isolation, PostgreSQL persistence/expiry and deletion. The invitation is passed through stdin, not argv. If any assertion fails, stop the rollout; the runner restarts a worker it stopped, leaves failure evidence and does not resubmit an uncertain job.
5. Recheck DeOpt/HBI HTTPS health and PIT-only exposure. Record a PIT resource snapshot at 5, 15, 60 minutes and 24 hours: CPU, RAM, host available memory, load/CPU pressure, disk free/growth, restarts, OOM, oldest queued job, worker processing time and HTTP 429/503. Do not admit real users during this canary.

The exact local Compose was exercised with disposable credentials: all four services started, migrations passed, API/worker/database became healthy, `HostConfig.PortBindings` was empty, and the smoke runner passed the event job through a PIT worker stop/start. Local cgroup checks proved all three running service limits. One local snapshot showed API 32.45 MiB, worker 31.83 MiB and database 38.19 MiB in use; these numbers must **not** be extrapolated to Netcup capacity. The source guard rejected deliberate router, host-port, proxy-network, NFT and database-egress mutations. No Netcup resource was created.

## Stop, evidence and PIT-only rollback

Stop immediately before traffic if any PIT service receives a public route, published host port or non-PIT network. Stop PIT API and worker if a neighbor healthcheck regresses; a PIT service OOMs or restarts unexpectedly; available host RAM remains below 2 GiB for five minutes; disk free falls below 25 GiB; CPU busy exceeds 85% for fifteen minutes; or the synthetic job is partial/failed, its queue age exceeds ten minutes, or the worker cannot recover. These are conservative canary thresholds, not promises of production capacity. Do not restart the shared proxy or neighboring services.

On failure, stop **only** PIT API and worker, capture sanitized PIT status/metrics and the failing assertion, and leave the PIT database volume intact until reviewed. The canary contains disposable synthetic/public-chain data only. After evidence review, remove only the exact `pit-crypto-backend-canary` resource and its named PIT networks/volume; destroy its disposable invitation, HMAC key and database password. Do not run broad Docker prune commands. A production-equivalent PIT `pg_dump`/restore procedure is documented in the V1.3 readiness note; no production backup schedule exists. Real users require a named PIT backup destination, retention and successful restore check before admission.

## Residual security and future private beta

The [manual image workflow](https://github.com/coriom/Pit/actions/runs/42965727618) reported 34 HIGH and one CRITICAL Trivy findings, with no fixed versions in that report. Most HIGH entries concern Debian utility/system packages not invoked by the Node API/worker; this limits their observed canary exposure but does not prove non-exploitability. Debian marks the Bookworm zlib MiniZip issue `CVE-2023-45853` ignored because that vulnerable MiniZip binary is not built in this package. Recheck the exact image and current advisories before launch; a newly actionable or reachable critical finding blocks the canary. The canary has no public route, no arbitrary NFT fetch, no untrusted user CSV and no SMTP. It still permits outbound RPC traffic, so complete network egress isolation is **not** claimed.

The browser-accessible private beta is a separate milestone: an operator-controlled DNS name, trusted HTTPS certificate covering that name, reviewed `/pit/api/v1/` Traefik route and proxy network, deployed Cloudflare Access gateway, HMAC/nonce/quota and direct-origin bypass tests, and PIT-only backups with verified restore. The current trusted IPv4 certificate expires 2026-11-14 22:57:16 UTC and does not cover an unspecified DNS hostname. Cloudflare Workers cannot fetch a literal origin IP. None of these later changes is part of the internal-canary authorization.
