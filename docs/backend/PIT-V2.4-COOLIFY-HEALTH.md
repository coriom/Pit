# PIT V2.4 — Coolify health reconciliation

## Evidence boundary

The deployed V2 Raw Application is `b8ohynbyx8dwsl5n46qdgjop` and its Compose project is `pit-crypto-v2-canary`. The approved V2 image and deployed Compose are unchanged. A fresh privileged, read-only snapshot on 2026-11-14 collected three bounded Docker observations. API, worker and PostgreSQL were `running/healthy`, with zero restarts, zero OOM flags and three successful recent healthcheck exits each. `pit-v2-migrate` was `exited` with exit code 0, zero restarts and no healthcheck. Coolify's stored and accessor status were both `degraded:unhealthy`; there were no additional servers and its only deployment job was `gauyvi93y4iaifghdsthwbg3|finished`.

The official Coolify 4.7.5 source (tag commit `378ce3735c4522ebb6b68e93b909b0511f278763`) explains this exact status: `PushServerUpdateJob::aggregateMultiContainerStatuses` collects Compose service states and calls `getExcludedContainersFromDockerCompose`. The exclusion helper accepts `exclude_from_hc: true` or **explicit** `restart: "no"`. `ContainerStatusAggregator::resolveStatus` returns `degraded:unhealthy` when its relevant services contain both running and exited containers. The stored Raw Compose was present and declared `pit-v2-migrate` with `RESTART=ABSENT` and `EXCLUDE=NO`; the other three services had `restart: unless-stopped`. Docker's implicit no-restart default does not satisfy Coolify's explicit-string check. The successful one-shot migration counted alongside three running services is the confirmed cause of the reported status. A status refresh alone cannot change that classification while this Compose remains stored.

Sources: [Coolify status collector](https://github.com/coollabsio/coolify/blob/v4.7.5/app/Jobs/PushServerUpdateJob.php), [exclusion rule](https://github.com/coollabsio/coolify/blob/v4.7.5/app/Traits/CalculatesExcludedStatus.php), [state resolver](https://github.com/coollabsio/coolify/blob/v4.7.5/app/Services/ContainerStatusAggregator.php).
