## Coolify 4.7.5 deletion behavior and limited scope

The [tagged `DeleteResourceJob`](https://raw.githubusercontent.com/coollabsio/coolify/v4.7.5/app/Jobs/DeleteResourceJob.php) defaults to `deleteVolumes=true` and `dockerCleanup=true`. The [tagged deletion UI handler](https://raw.githubusercontent.com/coollabsio/coolify/v4.7.5/app/Livewire/Project/Shared/Danger.php) also defaults its deletion checkboxes to true. A default Delete click is therefore outside this candidate's scope. [StopApplication](https://raw.githubusercontent.com/coollabsio/coolify/v4.7.5/app/Actions/Application/StopApplication.php) removes Compose containers and calls `deleteConnectedNetworks()` when `removeContainers=true`, even if a later deletion job is passed `deleteConnectedNetworks=false`. [Application::deleteConnectedNetworks](https://raw.githubusercontent.com/coollabsio/coolify/v4.7.5/app/Models/Application.php) disconnects `coolify-proxy` from the Application UUID network and removes that network. [Service deletion](https://raw.githubusercontent.com/coollabsio/coolify/v4.7.5/app/Actions/Service/DeleteService.php) separately accepts flags for volume/network/configuration removal.

The [candidate cleanup manifest](../../deployments/pit-netcup-cleanup-candidate-v1.json) therefore requires a stage-stop of the two Applications with `removeContainers=false,dockerCleanup=false`, then separate inspection. Any later resource deletion must pass `deleteVolumes=false,dockerCleanup=false,deleteConnectedNetworks=false,deleteConfigurations=true` explicitly and must account for the **two exact PIT management-network proxy detachments** that `StopApplication` still performs. Coolify may remove its local resource record even if remote cleanup fails; inspect Docker after each resource and stop on any drift. Only empty, proven PIT-owned private networks may be removed by exact name. No global Docker cleanup, proxy restart, CORIMOX change or volume deletion is in this manifest. The three PostgreSQL volumes and local PIT backup archives remain on Netcup under this candidate. A distinct destructive-data gate would require a fresh quiesced snapshot and restore before deleting them.

The readiness gates are **PIT_STOP_READY=NO**, **PIT_RESOURCE_CLEANUP_READY=NO**, **PIT_VOLUME_DELETION_READY=NO**, because the Control Plane and two neighbor containers are currently stopped. These are operational blockers to requesting a cleanup GO, not a reason to repeat the already verified PIT restores.

## CORIMOX portability

The [PIT portability candidate](../../deployments/pit-corimox-portability-candidate.json) preserves the exact Rust/PostgreSQL images, service modes, limits, healthchecks, secret names and private-network contract without secret values. It is deliberately marked **not deployable by the current CORIMOX API**. In source, CORIMOX `AppSpec` fixes the application port to 8080 and its reconciler fixes HTTP `/ready` and `/health` probes, always creates an Ingress and accepts only local-registry image digests. PIT uses API port 8789 with a versioned readiness path; its worker and migration need distinct command modes and no HTTP ingress. CORIMOX managed PostgreSQL currently uses a different image, database and role layout, and restoring PIT into it has not been tested. CORIMOX therefore needs reviewed support or an owned integration path and a separate Contabo acceptance before `CORIMOX_REDEPLOYMENT_READY` can become true. Data recoverability and a portable configuration contract do **not** constitute a hosted migration.

No hosted resource was stopped or deleted in this pass. The cleanup manifest is immutable after hashing but **not authorizable on the current host baseline**. When CORIMOX and the affected neighbors reach an explicitly accepted state, recheck the host and adjust the manifest only if resource identities or permitted effects changed; then request a new matching GO before execution.
